# DB を差し替えるためのリポジトリ層を作らず、テストでも本物の DB を使う

`server/poll` は Drizzle を直接使い、DB を抽象化するリポジトリ層(差し替え用のインターフェース)は作らない。libsql はメモリ上の DB(`file::memory:`)で動くため、テストでも本番と同じマイグレーションを当てた本物の SQLite を使える。差し替え先(テスト用の偽物)が要らないので、インターフェースを置いても実装が1つしかなく、間接層が増えるだけになる。

## Consequences

- テストは本物の SQL を通るため、モックでは通るが本番では失敗する、ということが起きない。
- DB アクセスは `server/poll/store.ts` にまとめ、外には見せない(内部のシームにとどめる)。DB を差し替えるときに直す場所は `server/db` とこのファイルに限られる。
- 差し替えに備え、SQLite 固有の SQL や関数は避け、Drizzle のクエリビルダーの範囲で書く。Cloudflare D1 は対話的なトランザクションに対応していないため、「読む → 判断する → 書く」を1つのトランザクションに詰め込みすぎない。
- Postgres に移る場合は、スキーマの定義とマイグレーションを作り直す。テストは PGlite(メモリ上で動く Postgres)で同じ方針を続けられる。
