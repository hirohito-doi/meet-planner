# 実装の進め方の記録

このアプリを作った手順を、どのスキルをどう使ったかを中心に記録する。作業が進むたびに追記する。スキルは mattpocock-skills(以下、スキル名だけを書く)。

## 全体の流れ

| 段階 | 使ったスキル | 主な成果物 | ブランチ |
| --- | --- | --- | --- |
| 1. 要件を詰める | grilling | docs/spec.md の初版 | main |
| 2. 用語と判断を固める | domain-modeling | GLOSSARY.md、ADR 0001〜0003 | main |
| 3. 操作感を確かめる | prototype(UI) | 候補を作る表の試作 | prototype/slot-grid |
| 4. 土台を作る | (スキルなし) | Next.js・Vitest・Playwright・Drizzle の雛形 | setup/scaffold |
| 5. モジュールを設計する | codebase-design | ADR 0004、`server/poll` の構成 | feature/poll-core |
| 6. 中身を作る | tdd | `server/poll`、`lib/jst`、`lib/slot-grid` | feature/poll-core |
| 7. 画面を作る | (tdd の決まりを流用) | 作成・回答・管理の3画面、E2E | feature/screens |
| 8. 触って直す | grilling 風の質問の繰り返し | 画面の手直し | feature/screens |

## 1. grilling: 要件を詰める(2026-11-20)

- 「調整さんのようなアプリ」という出発点から、質問を番号付きで何回かに分けて出し、それぞれに推奨の答えを付けた。答えは「推奨で良い」か、番号ごとの短い指示で返ってくる。
- 決まったことはその場で docs/spec.md に書いた。決まっていないことは「未決事項」として残した。
- 学び: 質問の意味が伝わらなかったときは、図と具体例で言い直すと通じた。抽象的な選択肢だけを並べない。

## 2. domain-modeling: 用語と判断を固める(2026-11-20)

- 「回答者」「回答」「未回答」「スコア」などの用語を GLOSSARY.md に定義した。使わない言い換え(_Avoid_)も書く。
- 後から理由を問われそうな判断を ADR にした。0001 はログインなしのリンク方式、0002 は自前の Node と SQLite、0003 はドラッグ1回で候補1件。
- 学び: 仕様が変わったら用語集も直す。例として、コメントをなくしたときに「回答」の定義を直した。

## 3. prototype(UI): 操作感を確かめる(2026-11-21)

- 問い: 「36時間の縦軸、ドラッグで候補を作る、重なった候補を横に並べる、スマホは2回タップ」で操作できるか。
- 本番と別のブランチ(prototype/slot-grid)に、捨てる前提の画面を作って触ってもらった。
- 分かったことを spec.md に書き戻し(8a9119a)、試作のコードは main に入れなかった。

## 4. 土台(2026-11-21)

- スキルは使わず、Next.js 16、Vitest、Playwright、Drizzle、libsql の雛形を作った。
- AGENTS.md の指示に従い、Next.js の書き方は `node_modules/next/dist/docs/` を読んでから決めた。学習データと違う点(`cacheComponents`、`PageProps` など)があるため。

## 5. codebase-design: モジュールを設計する(2026-11-21)

- 「深いモジュール」(小さなインターフェースの裏に多くの振る舞い)の考え方で、`server/poll` を設計した。
- アプリから使うのは `index.ts` の5つの関数だけ(`createPoll`、`readPoll`、`join`、`openResponse`、`openAdmin`)。
- 管理者の操作は `openAdmin` が返すオブジェクトからしか呼べない。回答者の操作は `openResponse` が返すオブジェクトからしか呼べない。トークンの照合を1か所に集めるため。
- リポジトリ層は作らない(ADR 0004)。テストはメモリ上の libsql を本番と同じマイグレーションで使う。

## 6. tdd: 中身を作る(2026-11-21)

- テストを書く場所(seam)を先にユーザーと決めた。`server/poll` のインターフェース、`ranking.ts`、`lib/jst`、`lib/slot-grid` の4つ。
- 1サイクルで1つのテストを書く。先に失敗(red)を確かめてから、通すだけの実装(green)を書く。
- テストが最初から通ってしまったときは、実装を一時的に壊してテストが落ちることを確かめる(ミューテーション)。壊すのは文字列置換で行い、`git checkout` では戻さない(ほかの未コミットの変更まで消えるため)。
- リファクタリングはサイクルの中でしない。
- 途中で仕様が「まとめて送信」から「セルごとの自動保存」に変わった。テストを新しい振る舞いで書き直してから実装を直し、古い関数(`respond`)は消した。

## 7. 画面を作る(2026-11-21)

- Server Action は `server/poll` を呼ぶだけにし、検証と権限の確認は `server/poll` に任せた。
- 主な流れ(作成 → 回答 → 確定)を Playwright の E2E で確かめる。PC とスマホ(Pixel 7)の両方で動かす。
- E2E はユーザーの開発サーバー(3000番)を止めないように、ビルドしたアプリを 3100番で起動する。
- 原因の調査で分かった Next.js 16.4.6 の問題: `partialPrefetching: true` だと、ページを読み込んだ直後の Server Action の結果が画面に反映されない。設定でオフにし、理由をコメントに残した。

## 8. 触って直す(2026-11-22)

- ユーザーが開発サーバーで触り、気になった点を1つずつ挙げる。進め方は次のとおり。
  1. 意図があいまいなら、番号付きの質問と推奨の答えを出す。
  2. spec.md(必要なら ADR と用語集)を直す。
  3. `server/poll` の振る舞いが変わるときは、tdd の手順で直す。例: 確定中の候補の削除、コメントの廃止。
  4. 画面だけの変更は E2E を足すか直す。実装を先に書いたときは、壊して E2E が落ちることを確かめる。
  5. 見た目の変更は、Playwright で画面を撮影して確かめる。
  6. 単体テスト、E2E、型チェック、lint を通してからコミットする。
- この段階で決まった主な変更:
  - 日付はカレンダーだけで選ぶ。
  - 横にドラッグすると、複数の日に同じ時刻の候補を作れる。ADR 0003 を改めた。
  - 確定中でも候補を削除できる。確定した候補を消すと、確定も取り消される。
  - 回答画面にスコアを出さない。
  - コメントをなくした。DB の列も削除した。
  - 回答画面の見やすさを上げた。
- 学び: 見た目の好みは、言葉より撮影した画面で確かめるほうが早い。また、確認なしに私が決めたこと(例: 確定中はカレンダーを隠す)は、報告のときに明記して覆せるようにしておく。

## 9. code-review: 変更をレビューする(2026-11-22)

- main から feature/screens までの43コミットを、`code-review` スキルで2つの観点に分けて見た。2つのサブエージェントを同時に動かし、互いの結果が混ざらないようにする。
  - Standards: AGENTS.md、仕様書のモジュール構成、ADR、用語集に沿っているか。加えて、Fowler のコードの臭い(重複、わかりにくい名前など)を判断材料として見る。
  - Spec: 仕様書の要件に足りないもの、頼まれていないもの、実装が間違っていそうなもの。
- 重い指摘は、報告の前にコードを読んで本当か確かめた。
- 指摘への対応は4種類に分けて、ユーザーの承認を得てから進めた。
  - 不具合を直す: 連続タップで表示が戻る、回答画面にスコアが送られる、スマホで候補の上を終了にできない。
  - 規約違反を直す: `rowid` で並べていた(ADR 0004 違反)。登録順の列を足した。
  - 仕様書を実装に合わせる: FormData の記述、確定中のカレンダー、頼まれていない小さな追加。
  - 臭いを整理する: 重複したチェック、型の置き場所、用語集にない名前。
- 不具合の修正は、E2E を足してから、直す前のコードに戻すと落ちることを確かめた。連続タップのテストは、最初は直す前のコードでも通ってしまった。条件(通信を遅らせる時間)を変えて不具合を再現できるようにしたところ、直した後のコードにも別の不具合(古い表示が一瞬見える)があると分かった。
- 学び: テストが通ったことより、「直す前に戻すと落ちる」ことのほうが確かめる価値がある。落ちないテストは、何も確かめていない。
- レビューの対応を終えたあと、ユーザーの承認を得て feature/screens を main にマージした(--no-ff。feature/poll-core の変更も含む)。リモートはまだない。

## 10. prototype(UI): デザインの方向を決める(2026-11-22)

- 問い: アプリ全体の見た目(配置、色、余白、文字、部品の形)をどの方向にするか。
- 比べる画面は作成画面にした(配置の違いがいちばん出るため)。3案は色ではなく配置が違うものにした。A は1列で作成ボタンを下に固定、B は2列、C はステップ式。色の雰囲気(白地に slate)は3案で同じにした。
- `prototype/design` ブランチで、`/?variant=A/B/C` と画面下の切り替えバー(開発サーバーだけで表示)で切り替えた。本物の作成処理まで動くので、触って比べられる。
- 撮影して確かめているうちに、共通の部品(カレンダーと表)の青だけが浮いていると分かり、slate に変えた。
- ユーザーが B を選んだ。決定は `prototype/design` に空のコミットで記録し、試作のコードは main に入れない。
- feature/design で B を本番用に書き直した(試作のコードは持ち込まない)。共通の部品(`app/_components/ui.tsx`: 帯、2列、見出し、ボタン、入力欄)を作り、作成・管理・回答の3画面に当てはめた。
- E2E は、候補の一覧に時刻が出るようになったため、表の候補を完全一致で探すように直した。スマホでは一覧が伸びて表がずれ、タップがずれた。テストを直すだけでなく、スマホでは一覧を表の下に置くように配置も直した。
- 学び: 開発中の Tailwind は一度見たクラス名を覚えていて、書き間違えたクラス名で CSS が壊れると、開発サーバーを起動し直すまで直らない。

## 11. 回答者が多いときの画面を確かめる(2026-11-22)

- ユーザーの依頼で、上限の50人と候補10件のデータを E2E 用のアプリに入れ、PC とスマホで撮影した。データは E2E 用の DB にだけ入れ、ユーザーの開発用 DB は使わない。
- 見つけた問題: 見出しの行が縦スクロールで消える、自分の列が右端にある、管理画面の回答者の一覧が長すぎる、管理画面のカレンダーが今月から始まる。ユーザーが4つとも直すことにした(一覧はスクロール)。
- スマホの撮影が止まり続けた。調べると原因は2つあった。1つは撮影の手順の誤り(PC 側で50人に達し、スマホで登録できなかった)。もう1つは本物の不具合で、回答者が多いと、スマホでページ全体が縮小表示されていた。
  - ページの幅を測り、要素を1つずつ隠して原因を絞った。○△× に添えた読み上げ用の文字(`sr-only`、絶対位置)が表の枠の外を基準に置かれ、ページの幅を押し広げていた。
  - 不具合を再現する E2E(スマホでページ幅が画面幅に収まる)を先に書いて落ちることを確かめ、アイコンを `relative` で包んで直した。
  - 途中で原因だと思って足した `min-w-0` は、外してもテストが通ったので外した。
- 学び: 止めた E2E のサーバー(3100番)は残ることがあるので、コマンドラインを見て確かめてから止める。長く止まるテストは、制限時間を短くしてエラーの中身を見ると早い。
- feature/design を軽く見直し、ユーザーの承認を得て main にマージした(--no-ff)。件数の書き方が作成画面と管理画面でそろっていない点は、次の仕上げで直す。

## 12. 使ってもらう前の仕上げ(2026-11-23)

- feature/polish で、リンクのプレビュー、ファビコン、見つからないとき・エラー・読み込み中の画面を作った。
- 書く前に `node_modules/next/dist/docs/` で、この版の決まりを確かめた。たとえばエラー画面の引数は `reset` ではなく `retry` になっている。Cache Components を使っているときのメタデータの扱いも確かめた。
- 秘密の URL を扱うアプリなので、全ページを `noindex` と `no-referrer` にした。管理画面のプレビューには日程調整のタイトルを出さない。
- E2E を先に通そうとして分かったこと:
  - 回答画面で `openGraph` を指定すると、親のプレビュー画像の指定が消える。親の指定を引き継いでから上書きするように直した。
  - 画面の枠を先に送る作りのため、見つからないときも状態コードは 200 になる。仕様書に書き、テストは画面の表示を確かめる形にした。
- `noindex` の設定とプレビュー画像の引き継ぎは、一時的に外すとテストが落ちることを確かめた。
- feature/polish をユーザーの承認を得て main にマージした(--no-ff)。

## 13. prototype(UI): 色合いを決める(2026-11-23)

- ユーザーの「色合いがシンプルすぎる、雰囲気が欲しい」を受けて、`prototype/colors` で色の案を比べた。今回は問いそのものが色なので、配置は変えずに色だけを変えた。
- 色を役割の名前(page、header、accent など)の CSS 変数に置き換え、`data-theme` で案を切り替えた。どの画面でも、画面下のバーで切り替えられる。
- 進み方: 温かい・爽やか・夜の3案 → 「違いが分からない」 → 色の面積を増やす(帯を塗る、表の見出しを塗る) → A を赤寄りとオレンジ寄りに → 背景を白く、ポイントを鮮やかに(A3・A4) → A4 を抑えめに(A5) → A5 の変化形と彩度違い → A5 に決定。
- 学び:
  - 色の違いは小さな部分だけでは伝わらない。並べた比較画像を作ると、話が早く進んだ。
  - 鮮やかな色の上の白い文字は読みにくい。抑えめの色に濃い文字を載せる形にすると、印象を保ったまま読みやすくできた。
- 本番には、役割の名前で色を指定する仕組みと A5 の値だけを入れ、切り替えバーと他の案は入れなかった。小見出しは、淡いオレンジの文字だと読みにくいので濃い茶色にした。ファビコンとプレビュー画像も新しい色にそろえた。
- feature/colors をユーザーの承認を得て main にマージした(--no-ff)。

## 14. 候補の表の時刻を大きくする

- 「時間が細かすぎて見づらい」を、最初は行の高さを広げる依頼と受け取って直し始めた。途中でユーザーから「時刻の文字が小さいのを直して」と訂正があり、行の高さ・ブロックの文字・罫線の変更は戻した。
- 変更は時刻の目盛りだけ: 10px → text-sm(14px)、太さ medium、色を一段濃く。「前18:00」が収まるように目盛りの列を w-12 → w-16 に広げた。
- 確認は既存の E2E(行の高さに依存するマスの座標は変わらない)と、一時的なスクリーンショット用テスト(e2e/zz-*.spec.ts、確認後に削除)。
- 学び: 見た目の依頼は、どこを変えるかを最初に一言で確かめると手戻りが減る。
- 続けて、候補のブロックの中の時刻(「10:00-12:00」)も 10px → text-xs(12px)にした。「デザインに支障がない程度に」という依頼なので、30分の候補(高さ 22px)とスマホの狭い列に収まる大きさで止め、PC とスマホのスクリーンショットで確かめた。
- feature/grid-size をユーザーの承認を得て main にマージした(--no-ff)。

## 15. トップを紹介ページにする

- ユーザーの「トップはサービスの簡単な紹介の方が良い」に対し、4つの質問(ページの分け方、載せる内容、見た目、帯とリンク)を推奨付きで出し、「推奨で良い」で決めた。
- tdd スキルの流れ: 先に e2e/landing.spec.ts(トップは紹介でフォームがない、作成ボタンと帯のリンクで /new に進める、ロゴで戻れる)を書いて失敗を確かめ(red)、e2e/helpers.ts の作成画面の URL を `/new` に変えてから実装した(green)。
- 作成フォームと作成の Server Action は `git mv` で `app/new/` に移した(履歴を残すため)。帯の右は、画面の名前がないときだけ「日程調整を作る」のリンクにした。
- PC とスマホの全体のスクリーンショットを一時的なテスト(e2e/zz-*.spec.ts、確認後に削除)で撮って確かめた。docs/spec.md の「画面のデザイン」に紹介ページを書き足した。
- ユーザーの「3つのカードではなく、ひとつの枠で」を受けて、使い方と特徴をそれぞれ1つの枠にまとめ、中を区切り線(divide-x / divide-y)で分けた。PC とスマホのスクリーンショットで確認した。
- 続けて「1・2・3は縦に、境界の線はなし、外の枠は残す」を受け、使い方だけを縦並び(番号は左、見出しと説明は右)にした。特徴は指示がなかったので変えていない。
- 「特徴も同様に、『特徴』という文言は不要」を受け、特徴も1つの枠の中で縦並び・線なしにし、見出しを消した(section に aria-label="特徴" を残し、読み上げでは区切りがわかるようにした)。

## 16. サービス名を「○△× 日程調整」にし、帯の名前を見やすくする

- 名前はユーザーが決めることなので、案を4つ(推奨付き)と、変える範囲、帯の見せ方を質問した。ユーザーは「○△× 日程調整」を選んだ。残りは推奨で進めたが、帯はアイコンの代わりに ○△× を色付きのマークで描いた(名前に ○△× が入るので、アイコンと並べるとマークが2回続くため)。
- 先に E2E のタイトルとリンク名の期待値を新しい名前に変え、失敗するのを確かめてから実装した(red → green)。プレビューのサイト名(og:site_name)の確認も足した。
- 名前は app/_lib/site.ts の1か所にまとめた。○△× のマークは紹介ページと帯で使うので ui.tsx の Marks にまとめた。
- localStorage のキー(meet-planner:...)は画面に出ない内部の名前で、変えると回答者が自分の回答を見失うので変えなかった。
- プレビュー画像は日本語の書体がないため英字の名前を消し、○△× だけを大きく描いた。
- feature/landing と feature/brand をユーザーの承認を得て、この順に main にマージした(--no-ff)。

## 17. 画面の文言とドキュメントの日本語を見直す(natural-japanese スキル)

- natural-japanese スキルをクイックモードで使った。ドキュメントには lint.py(--genre tech)をかけ、画面の文言はソースから日本語の行を抜き出して目で読んだ。
- lint の指摘は少なかった。直したのは用語集の翻訳調「取り消すことができる」だけ。用語集の「_Avoid_:」の繰り返しと、仕様書の文長の均質さは、書式による指摘なので残した(判断台帳の「残す」)。
- 目で読んで直したのは次の種類:
  - 画面: 「作成する」と「作る」の混在を「作る」にそろえた。「確定中は」を「確定している間は」に(処理中と誤解されないように)。名詞と動詞が混ざった列挙(「回答・候補の追加・タイトルと説明を変更できません」)を直した。「共有します」「紛失」「復旧」を平易な語に。サーバーのエラーメッセージも同じ言い方にそろえた。

## 24. Cloudflare Workers へのデプロイを試す(spike/cloudflare、マージしない)

- ユーザーの依頼「試作してみて」。prototype スキルの「使い捨ての試作で問いに答える」に沿い、問いを「今のアプリは OpenNext + D1 で Workers の上で動くか」に決めた。ブランチは spike/cloudflare(main から)。
- 変えたこと: @opennextjs/cloudflare と wrangler を足し、wrangler.jsonc(D1 の DB、マイグレーションのフォルダ)と open-next.config.ts を作った。アプリが使う getDb() を D1 に替え、Db の型を libsql と D1 の両方が満たす形に広げた。server/poll は変えていない。単体テストは libsql のまま通る。
- Windows では OpenNext のビルドが、シンボリックリンクを作れずに失敗した(EPERM)。ユーザーの選択で、WSL の Ubuntu のホームに Node 24 を公式の配布ファイルから入れ(チェックサムを確認、管理者権限なし)、リポジトリを WSL 側に複製してビルドした。
- WSL ではビルドが通ったが、`wrangler dev` で開くと静的なトップページも含めて 500 になった。Next.js が「setTimeout の実装のため Cache Components の動作を保証できない」と警告し、描画が止まったまま Workers に打ち切られていた。互換性フラグ(no_handle_cross_request_promise_resolution)で別のエラーを消しても、止まるだけで直らなかった。
- このアプリが Cache Components に頼っているのは2画面の <Suspense> だけだったので、cacheComponents を切って試した。全画面が応答し、E2E を Workers のプレビュー(:8787)に向けると 28 件すべて通った(4件はもともと飛ばすテスト)。回答画面と管理画面の Cache-Control は `private, no-cache, no-store` だった。
- 結論: Cloudflare にするなら cacheComponents を切る必要がある。切ると回答画面と管理画面は毎回すべて描くので、外側を先に返す速さは失う。ビルドは Windows ではできず、WSL か CI(Linux)で行う。
- まだ確かめていないこと: 本物の Cloudflare への公開(アカウントと wrangler login が必要)、Windows での `pnpm dev`(D1 をまねる仕組みが Windows で動くか)。この試作のコードでは、getDb() が Workers の中でしか動かないので、Node で起動する今の E2E の設定(next start)はそのままでは動かない。
- 学び: WSL で `pkill -f workerd` を `bash -c` の中で使うと、自分のコマンド行にも当たって自分を止めてしまう。後ろに続けた書き換えが実行されていなかった。

## 27. 公開を Cloudflare の Workers Builds に任せる(docs/workers-builds)

- ユーザーから公開の手順を聞かれ、WSL の複製でビルドして `pnpm cf:deploy` を実行する手順を出した。「手元でビルドが必要か」と聞かれて、Cloudflare 側でビルドする Workers Builds を初めて案として出し、ユーザーはそちらを選んだ。
- 学び: 最初の質問(公開を「手順だけ用意」か「一緒に今やる」か)は、どちらも手元から公開する前提で、Workers Builds を選択肢に入れていなかった。「CI は Cloudflare に触らない(トークンを置かない)」と決めたことで、手で公開するしかないと思い込んでいた。Windows ではビルドできないとわかった時点で、手元でビルドしない方法と比べて出すべきだった。
- Cloudflare と OpenNext の公式ドキュメントを web-fetch のエージェントで確かめた: Worker の名前は wrangler.jsonc の name と同じでないとビルドが失敗する。Node は .node-version、pnpm は packageManager の版が使われる。`d1 migrations apply --remote` は CI では確認を飛ばす(バックアップは取る)。プレビュー版は本番の設定を引き継がない。
- `cf:deploy` からビルドを外し、Workers Builds の Build command(`pnpm cf:build`)と Deploy command(`pnpm cf:deploy`)に分けた。`.node-version` を足した。プレビュー版は使わないことにして、README の手順でオフにするよう書いた。ADR 0005 と README を書き換えた。

## 31. 回数制限を付ける(feature/rate-limit)

- ユーザーの依頼「回数制限をつける」。4つを質問し、対象は作成と回答の開始だけ(推奨)、回数は作成 5回/分・回答の開始 30回/分(推奨)、文言は短く「しばらく待ってから、もう一度お試しください。」、テストは単体テストで確かめて E2E では制限を外す(推奨)になった。
- 仕組みは Cloudflare Workers の Rate Limiting の binding(wrangler.jsonc の ratelimits)。キーは CF-Connecting-IP。判定は server/poll ではなく Server Action の入口で行う(DB の外の仕組みで、Workers の中でしか使えないため)。ActionResult の code に RATE_LIMITED を足した。
- tdd の流れ: 中身(applyRateLimit)を binding と同じ形の偽物の制限で確かめる単体テストを4件先に書き、モジュールがなくて失敗することを確かめてから実装した。止める行を消す変異でテストが失敗することも確かめ、$TEMP のバックアップから戻した。binding と要求の見出しを読む部分(rate-limit-context.ts)は分けた。
- WSL のプレビュー(制限あり)で、一時的なテストで作成を6回続けると6回目に文言が出て止まることを確かめた。手元の wrangler dev も制限をまねて数える。E2E は `--var RATE_LIMIT:off` で外したプレビューと Node の両方で 28 件通った。
- isWorkers() を server/runtime.ts に移し、DB の入口と回数制限で共有した。
- feature/rate-limit をユーザーの承認を得て main にマージし、GitHub に送ってからブランチを削除した。
- 本番で、一時的なテスト(コミットしない)で作成を続けたところ、6件作れて7回目で「しばらく待ってから、もう一度お試しください。」が出た。Cloudflare の数え方はおおよそ(拠点ごと)なので、設定の5回ちょうどでは止まらないことがある。作った6件はテストの中で管理画面から削除し、開くと「ページが見つかりません」になることを確かめた。回答の開始(30回/分)は同じ仕組みなので、本番では試していない。

## 32. 古い日程調整を自動で削除する(feature/data-retention)

- ユーザーの依頼「古いデータを自動で削除する」。決まりは推奨の案になった: 最後の候補の日から90日を過ぎたら、確定しているかどうかに関係なく、候補・回答・可否とともに削除する。仕組みは Cloudflare の Cron Triggers で1日1回(3:00 JST = 18:00 UTC)。作成画面と管理画面に短い案内を出す。
- ユーザーの依頼で、サブエージェントが別の worktree(E:\projects\meet-planner-retention)で実装した。main の作業と同じフォルダを触らないため。
- 候補が0件の日程調整は、主催者が最後の1件を削除するとできる(仕様書の「管理画面」に書いてある)。polls に作成日時(created_at)があるので、そのときは作成日時から数えることにした。スキーマは変えていない(マイグレーションなし)。
- 境目は「ちょうど90日までは残し、過ぎたら削除」にした。1日1回しか動かないので、実際に消えるのは過ぎた後の最初の 3:00。
- tdd の流れ: 先に `server/poll` の `deleteExpiredPolls(db, now)` の単体テストを10件書いた(90日を過ぎたものは候補・回答・可否まで消える、90日以内は残る、ちょうど90日の境目、古い候補と新しい候補が混ざると残る、確定中も消える、ほかの日程調整には触らない、候補0件は作成日時で数える、120件まとめて消せる)。関数がなくて失敗することを確かめてから実装した。変異の確認は4通り(境目の `<` を `<=` に、50件ずつの2回目以降を飛ばす、可否の削除を外す、日数を1日減らす)で、どれもテストが失敗した。実装は $TEMP のバックアップから戻した。
- 消す ID を先に読んでから、50件ずつ db.batch で消す。D1 は1つの SQL に渡せる値が100個までで、対話的なトランザクションもないため。今までの deletePoll も、この複数件版を使う形にまとめた。
- Worker の入口は OpenNext の手順「Custom Worker」に沿って `worker.ts` を作り、wrangler.jsonc の main をそこに替えた。fetch は `.open-next/worker.js` のものをそのまま渡し、scheduled で D1 の binding から DB を作って `deleteExpiredPolls` を呼ぶ。D1 から DB を作る部分(`server/db/d1-db.ts`)は、要求を処理するときの getDb と共有した。90日の決まりは server/poll、いつ動かすかは worker.ts が持つ。
- 案内の文言「最後の候補の日から90日たつと、自動で削除されます。」は、先に Node の E2E(主要な流れ)に足して失敗を確かめてから出した。日数は server/poll の RETENTION_DAYS をページから渡す。
- WSL に新しい複製を作って Workers 向けにビルドし、`pnpm cf:preview --test-scheduled` で起動した。手元の D1 に、100日前に終わった日程調整、候補0件で100日前に作った日程調整、古い候補と10日前の候補が混ざった日程調整を入れ、`/__scheduled?cron=0+18+*+*+*` を開くと「2件削除しました」とログに出て、混ざった日程調整とその回答だけが残った。Workers のプレビューに Windows から E2E を流して 28 件通った(4件はもともと飛ばすテスト)。
- 学び: worktree の .git はファイルで、中身が Windows のパス(E:/...)なので、WSL から worktree のフォルダを複製すると失敗した。ブランチは本体のリポジトリと共有しているので、本体の .git から `-b feature/data-retention` で複製した(読むだけで、本体は変えない)。
- 学び: `wsl -e bash -lc '... &'` で裏に回したプレビューは、wsl のコマンドが終わると一緒に止まった。プレビューは Bash ツールの run_in_background で動かし続けた。
- 学び: `.open-next/worker.js` はビルドの前にはなく、後にはあるので、型の確認を `@ts-expect-error` で黙らせると、ビルドした後の型チェックで「不要な指示」として失敗する。OpenNext の例どおり `@ts-ignore` にして、lint の規則だけその行で外した。
- main へのマージと GitHub への送信はしていない(ユーザーの判断を待つ)。
- ユーザーの承認を得て feature/data-retention を main にマージした。process-log の末尾が main 側の追記(本番の回数制限の確認)とぶつかったので、両方を残した。
